# AGENTS.md

## Назначение

Этот репозиторий — продукт RINIR для мониторинга давления медицинских газов. Целевая среда — Debian 13 amd64, Docker Compose, Chromium kiosk. Среда разработки и программного FAT — Windows 10/11 с Docker Desktop.

Проект считается полноценным продуктом, а не временным MVP. Не добавлять «временные» заглушки, непроверяемые обходы или дублирующие пути конфигурации.

## Источники истины

1. `scripts/generate-product-flow.mjs` — исходное описание продуктового Node-RED flow и Dashboard.
2. `flows/flows.json` — единственный рабочий flow, сгенерированный из указанного скрипта.
3. `docker/compose.yaml` и overrides `docker/compose.fat.yaml`, `docker/compose.production.yaml` — фактическая топология runtime.
4. `deploy/debian/` и `factory/` — заводская установка, firstboot, systemd, kiosk, firewall и acceptance.
5. `docs/00-прочитать-сначала.md` и `docs/01-развертывание-стенда.md` — операторская последовательность.
6. `docs/29-реестр-источников.md` — происхождение исходного flow и аудитов.

Материалы в `docs/source/` и `docs/audit/` — исторические evidence, а не актуальные runtime-инструкции. При расхождении актуальный код и проверенный runtime имеют приоритет.

## Обязательный порядок изменения flow

1. Изменить `scripts/generate-product-flow.mjs`.
2. Выполнить `npm run generate:flow`.
3. Не редактировать `flows/flows.json` вручную: такие изменения будут потеряны при следующей генерации.
4. Обновить контрактные тесты в `tests/product-flow.test.mjs` и `tests/runtime-render.test.mjs`.
5. Прогнать полный `npm test`, а не один выбранный тест.
6. При изменении HMI пересобрать FAT-стенд и проверить фактический Dashboard в браузере.

## Аппаратный контракт

- Шлюз по умолчанию: USR-DR134, `192.168.50.10:502`, Modbus TCP ↔ RTU, `115200 8N2`.
- За одним шлюзом допустимы ровно один WB-MAI6 и ноль или один WB-MR3LV/I.
- Unit ID сканируются при firstboot и могут быть изменены в сервисном UI. Не возвращать жёсткую runtime-привязку к `65`/`66`.
- Входы: O₂—`IN1P`, AIR—`IN2P`, VAC—`IN3P`, N₂O—`IN4P`, CO₂—`IN5P`, обратная связь клапанов—`IN6P`.
- IN1P…IN5P: `4–20 мА`, scale `0…100`; Node-RED читает базовый 32-битный токовый регистр. Ток ниже `3.5 мА` означает `НЕТ ДАННЫХ`, `3.5…4 мА` соответствует `0.0 bar`, `4…20 мА` линейно пересчитывается в `0.0…10.0 bar`.
- IN6P: сухой контакт, `1` — штатный режим, `0` — аварийный.
- Активные газовые каналы выбираются в UI. Допустимо от 3 до 5. Неактивный канал не опрашивается, не влияет на статус/клапаны и не отображается.
- Автоматическое управление WB-MR3LV/I по умолчанию выключено. Не включать его без аппаратного FAT.
- WB-MR3LV/I K1 выдаёт один общий удерживаемый сигнал внешней автоматике. Все активные газы могут быть причинами команды; не описывать их как пять независимых релейных выходов.
- Запись регистров разрешена только в commissioning/autoconfigure и в явно согласованном тесте. Обычная диагностика — read-only.

## Runtime и данные

- Node-RED Dashboard: `/dashboard/monitoring`, `/dashboard/history`, `/dashboard/events`, `/dashboard/engineering`.
- Полноэкранный monitoring должен быть пригоден для `1366×768` и `1920×1080` без внешней прокрутки.
- Опрос сериализован: не добавлять параллельные Modbus-запросы на RTU.
- `2147483647` и `-2147483648` в базовом 32-битном регистре не являются током и переводят канал в `НЕТ ДАННЫХ`.
- Переходы состояний должны сохранять гистерезис и таймаут stale-data; не возвращать дребезг `НОРМА ↔ НЕТ ДАННЫХ`.
- InfluxDB retention — 365 суток. Изменение schema, measurement, tags и retention требует обновления backup/restore и capacity-расчёта.
- Runtime-настройки, объект, пороги и реестр исполнителей хранятся в persistent Node-RED context.

## Доступ и секреты

- `.env`, factory env, credentials, токены MAX, InfluxDB token и пароли не коммитятся.
- В документации указывать имена переменных и пути получения credentials, но не фактические секреты.
- Локальный kiosk открывает только monitoring. Удалённый доступ идёт через HTTPS/nginx и отдельную аутентификацию.
- Изменения объекта и порогов должны быть привязаны к исполнителю, аутентифицированному персональным кодом.
- Не выводить секреты в logs, evidence, test snapshots и Git diff.

## Стиль изменений

- Документация и UI — на русском. Все поясняющие комментарии в исходном коде, скриптах и конфигурационных файлах также должны быть на русском. Не переводить машинные директивы (`shebang`, `shellcheck`, `#_preseed_V1`), filenames, API, Modbus fields, команды и технические идентификаторы.
- Менять только то, что необходимо для задачи. Не перезаписывать и не удалять несвязанные незакоммиченные изменения.
- Не использовать `git reset --hard`, рекурсивное удаление или `down --volumes` без прямого указания.
- Версии образов и dependencies оставлять pinned. Любое обновление версии требует release-проверки.
- Новая runtime-переменная должна появиться в `.env.example`, Compose, Debian generator, `docs/07-конфигурация.md` и contract-тесте.

## Проверки

Минимум для любого изменения:

```powershell
npm run generate:flow
npm test
git diff --check
```

Дополнительно по области:

```powershell
npm run audit:flow
npm run audit:secrets
npm run docs:check
.\scripts\simulation.ps1 start
.\scripts\simulation.ps1 normal
.\scripts\simulation.ps1 oxygenalarm
.\scripts\simulation.ps1 nodata
.\scripts\simulation.ps1 status
```

Для Debian/factory-изменений также обязательны:

- `bash -n` для всех изменённых shell-скриптов;
- `docker compose ... config --quiet` для base/FAT/production Compose;
- прогон `scripts/release-check.ps1` перед сборкой образа;
- проверка нового ISO по `docs/09-проверка-релиза.md`.

## Критерии готовности

Изменение готово, когда:

1. исходная логика, сгенерированный flow, tests и docs не противоречат друг другу;
2. пройден полный автоматический набор проверок;
3. изменённый UI проверен в фактическом Dashboard;
4. сохранена обратная совместимость или описана явная миграция;
5. не затронуты посторонние локальные изменения и не раскрыты секреты;
6. оставшиеся аппаратные проверки чётко отделены от уже пройденных software-проверок.

## Контекст проекта

### Назначение

Проект — тестовый стенд мониторинга давления медицинских газов O₂, AIR и N₂O для реанимации или аналогичного помещения. Интерфейс предназначен прежде всего для врачей, а не технических специалистов.

Главный экран должен показывать:

- крупное числовое давление;
- единицу `bar`;
- понятный статус;
- цветовую зону;
- общий статус системы;
- явную потерю данных.

Согласованные статусы:

- `НОРМА` — зелёный;
- `ВНИМАНИЕ` — жёлтый;
- `ТРЕВОГА` — красный;
- `НЕТ ДАННЫХ` — серый.

Цвет не должен быть единственным носителем информации.

### Заявленная целевая настройка USR-DR134

- IP: `192.168.50.10`;
- Work Mode: `TCP Server`;
- Local port: `502`;
- Modbus mode: TCP ↔ RTU simple protocol conversion / `CONVERT`;
- serial: `9600`, 8 data bits, no parity, 1 stop bit;
- MQTT, EDGE, autonomous polling, JSON reporting, heartbeat и registration packet отключены, если сбор выполняет Node-RED.

Были заявлены проблемы физики RS-485. Симптом: COM/LINK и WB-MAI6 мигают, но `mbpoll` получает timeout. По сообщениям проблема устранилась после переобжима/переподключения, однако первичные логи до и после отсутствуют.

### WB-MAI6

Заявленный Slave ID: `65`.

Для стандартного входа 4–20 мА официальный код типа:

```text
HEX 0x1302
DEC 4866
```

Адреса трёх каналов согласуются с официальной картой WB-MAI6:

| Газ | Канал | Тип, holding | Нижняя граница, holding i32 | Верхняя граница, holding i32 | Значение, input i16 |
|---|---|---:|---:|---:|---:|
| O₂ | IN1P | 5120 | 5128 | 5130 | 5380 |
| AIR | IN2P | 9216 | 9224 | 9226 | 9476 |
| N₂O | IN3P | 13312 | 13320 | 13322 | 13572 |

Для датчика 0–16 bar заявлена шкала `0…160`, после чего Node-RED должен делить пересчитанное значение на `10`.

Официальная карта указывает `0x7FFF`, то есть `32767`, как ошибку пересчитанного 16-битного значения. `-32768` можно оставить как защитный фильтр, но он не подтверждён доступной строкой официальной карты как основной код ошибки WB-MAI6.

Критерии успешной настройки:

1. Тип каналов читается как `4866`.
2. Границы читаются как `0` и `160`.
3. Значения 5380/9476/13572 не равны коду ошибки при исправной петле.
4. При 4/12/20 мА ожидаются примерно 0/80/160.
5. Конфигурация сохраняется после power cycle.

### Подключение двухпроводного PT-506

Заявленная схема:

```text
+24 VDC → красный провод PT-506
чёрный провод PT-506 → INxP
iGND канала → 0 VDC источника
INxN не используется для одного датчика на P
```

`iGND` — сигнальная земля аналогового входа, не защитное заземление PE. Перед реальным подключением сверить паспорт конкретного PT-506 и официальную схему WB-MAI6.

### Давление и расход

Сейчас измеряется давление `P`, единица `bar`.

Не показывать `Q` и `м³/ч`, потому что расход нельзя корректно вычислить только из одного статического давления. Для расхода в будущем нужны отдельные расходомеры, дифференциальное давление на известном сужающем устройстве либо цифровые Modbus-устройства. Любое добавление расхода — отдельная согласуемая функция.

## Желаемая логика обработки

Это спецификация для обсуждения, а не разрешение немедленно переписать flow.

Для каждого газа:

```text
raw = msg.payload[0] или согласованное поле node-red-contrib-modbus

если raw == 32767
или raw == -32768
или значение отсутствует
или не является конечным числом
или данные старше timeout:
    status = nodata
иначе:
    pressure_bar = raw / 10
```

Тестовые пороги:

```text
4.0 ≤ bar ≤ 6.0       → ok / НОРМА
3.5 ≤ bar < 4.0       → warn / ВНИМАНИЕ
6.0 < bar ≤ 6.5       → warn / ВНИМАНИЕ
bar < 3.5 или > 6.5   → alarm / ТРЕВОГА
```

Эти пороги не являются клинически утверждёнными. До продакшн-внедрения получить владельца требований и отдельные пороги для каждого газа.

Нужно согласовать:

- polling interval;
- stale/nodata timeout;
- hysteresis;
- time delay перед тревогой;
- приоритет общего статуса;
- правила восстановления;
- хранение и отображение `nodata`.

Предлагаемый безопасный приоритет общего статуса для обсуждения:

```text
alarm > nodata > warn > ok
```

## Требования к MAX

MAX в доступном flow отсутствует.

Желаемая логика:

```text
ok → warn       уведомление
ok → alarm      уведомление
warn → alarm    уведомление
alarm → ok      восстановление
nodata → ok     восстановление
любой → nodata  уведомление после выдержки
alarm → alarm   повтор через N минут
```

Не отправлять сообщение при каждом чтении.

До реализации запросить:

- подтверждённый MAX API;
- тестовый bot token;
- chat ID или список получателей;
- правила для warn/alarm/nodata;
- reminder interval;
- retry/backoff;
- текст сообщения;
- правила эскалации;
- требования к журналированию.

Токен хранить только в environment/secret storage.

- persistent volumes;
- `.env` для локальных секретов;
- optional Modbus simulator только после согласования.

Если Docker Desktop недоступен по политике или лицензированию, предложить минимальную альтернативу через Docker Engine внутри WSL2. Не выбирать молча.

### Локальное тестирование без оборудования

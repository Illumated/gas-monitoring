# Архитектура

## Назначение

Система получает давление линий O₂, AIR и N₂O, показывает текущее состояние на настенном экране и сохраняет историю. Интерфейс предназначен прежде всего для медицинского персонала и должен явно отличать норму, предупреждение, тревогу и отсутствие данных.

## Наименования каналов

| Код | Название на экране | Значение |
|---|---|---|
| `O₂` | Кислород | Линия медицинского кислорода. |
| `AIR` | Медицинский воздух | Линия медицинского воздуха для дыхательных систем. |
| `N₂O` | Закись азота | Линия закиси азота. |

Термин «медицинский воздух» соответствует ГОСТ Р ИСО 7396-1-2011. Его нельзя автоматически распространять на отдельную линию сжатого воздуха 7–8 бар для привода хирургических инструментов. Фактическое назначение линии `AIR` подтверждается по проекту газоснабжения объекта во время пусконаладки.

Официальный источник: [ГОСТ Р ИСО 7396-1-2011 — Росстандарт](https://protect.gost.ru/gost/details/d5e43799-26a4-4541-b6b1-64dcdda9247f).

## Целевая аппаратная схема

```text
PT-506 O₂  4–20 mA ─┐
PT-506 AIR 4–20 mA ─┼─> WB-MAI6, Modbus RTU
PT-506 N₂O 4–20 mA ─┘          │
                               v
                   USR-DR134, Modbus TCP
                               │
                               v
                    Node-RED processing
                      │              │
                      v              v
                  Dashboard       InfluxDB
```

Физическое наличие, подключение и текущие настройки оборудования пока не подтверждены runtime-доказательствами.

## Контейнерная схема

```text
Windows 10 / Docker Desktop / WSL2
└── Compose project gas-monitoring
    ├── node-red
    │   ├── image: product-specific pinned build
    │   ├── port: 127.0.0.1:1880
    │   └── volume: node-red-data
    └── influxdb
        ├── image: InfluxDB OSS 2 pinned version
        ├── port: 127.0.0.1:8086
        ├── volume: influxdb-data
        └── volume: influxdb-config
```

Порты публикуются только на loopback. Связь контейнеров выполняется по внутренней сети `backend`.

## Владение конфигурацией

- Git хранит `flows/flows.json`, Docker Compose, настройки без секретов, тесты и документацию.
- Docker image содержит проверенную рабочую версию flow и palette dependencies.
- При старте репозиторный flow разворачивается в persistent Node-RED volume.
- Локальный `.env` содержит только конкретные секреты и не хранится в Git.
- Runtime-изменения через Node-RED editor должны быть экспортированы обратно в репозиторий до следующего развёртывания.

## Требуемая обработка отказов

- Ошибка датчика или специальное значение не преобразуется в давление.
- Потеря Modbus-данных переводит канал в `НЕТ ДАННЫХ` за утверждённый timeout.
- Старое корректное значение не должно бесконечно отображаться как норма.
- Недоступность InfluxDB не должна останавливать текущую индикацию.
- Перезапуск контейнера не должен уничтожать историю, context или credentials.

## Реализованный программный профиль

- единый последовательный цикл O₂ → AIR → N₂O длительностью `1000 ms`;
- задержка очереди между Modbus-командами `300 ms`, параллельные запросы запрещены;
- переход в `nodata` через `4000 ms` без корректного значения;
- актуальность всех каналов проверяется единым HMI-state узлом по `updatedAt`; индивидуальные stale-таймеры для измерений не используются;
- одиночный пустой Modbus-ответ не сбрасывает последнее показание; документированные invalid-коды обрабатываются немедленно;
- приоритет общего статуса: `alarm` → `nodata` → `warn` → `ok`;
- запись measurement `gas_pressure` через InfluxDB v2 HTTP API;
- локальные страницы `/dashboard/monitoring` и `/dashboard/history`;
- отдельный FAT-профиль поднимает Modbus TCP simulator; внутреннего обхода Modbus в product flow нет;
- пороги каждого газа и гистерезис задаются environment-параметрами;
- подтверждённые сервисные изменения порогов сохраняются в persistent context и журналируются;
- `gas_pressure` хранит измерения, `gas_event` — переходы состояния и изменения конфигурации;
- retention обоих типов данных составляет 365 суток;
- переходы состояния могут отправляться в MAX, интеграция по умолчанию отключена.

Назначение и допустимые сочетания environment-параметров описаны в [configuration.md](configuration.md).

Клинические пороги, физическое оборудование и производственная схема доступа требуют отдельного протокола приёмки; это не скрывается программным статусом.

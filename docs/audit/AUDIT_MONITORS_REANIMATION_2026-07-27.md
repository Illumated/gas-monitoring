Дата аудита: 27 июля 2026 года

## Краткое резюме

1. Проект описывает тестовый стенд контроля давления медицинских газов O₂, AIR и N₂O с интерфейсом для врачей.
2. Предполагаемый тракт: датчики PT-506 4–20 мА → WB-MAI6 → RS-485 → USR-DR134 → Ethernet → Node-RED.
3. В локальном зеркале проекта каталог `sources/` существует, но пуст.
4. Экспорты чатов/топиков, изображения, `flows.json`, логи Node-RED, InfluxDB и Modbus в доступных материалах отсутствуют.
5. Единственный содержательный внутренний источник — приложенное текстовое задание; оно фиксирует заявленный контекст, но не является доказательством текущего runtime-состояния.
6. Официальная документация подтверждает возможности WB-MAI6, режим 4–20 мА, карту регистров и код типа датчика `4866`.
7. Адреса конфигурации и значений трёх каналов из задания согласуются с формулами официальной карты регистров.
8. Значение `32767` (`0x7FFF`) подтверждается документацией как ошибка пересчитанного 16-битного значения WB-MAI6.
9. Утверждения о реально восстановленной связи, текущем Node-RED flow, работающем dashboard и записи истории подтвердить невозможно без первичных артефактов.
10. Пороговые значения `4.0–6.0`, `3.5–6.5 bar` следует считать тестовыми, а не клинически утверждёнными.
11. `wb` указан как вероятный актуальный InfluxDB bucket, но это не подтверждено конфигурацией.
12. MAX-уведомления, kiosk-режим, резервирование питания/сети и эксплуатационная документация не подтверждены как реализованные.
13. Главный блокер завершения аудита — отсутствие `flows.json`, скриншотов, логов, конфигураций и протокола испытаний стенда.
14. Минимальный демонстрационный MVP возможен после проверки трёх токовых петель, фиксации flow, локальной истории и полноэкранного dashboard; MAX можно вынести в следующий этап.

## 1. Краткое описание проекта

### Подтверждённые факты

- Локальное зеркало имеет название «Мониторы реанимации».
- Задание определяет проект как тестовый стенд мониторинга давления медицинских газов/датчиков давления.
- Целевая аудитория интерфейса — врачи и другие нетехнические пользователи.
- Интерфейс должен приоритетно показывать понятное состояние: «Норма», «Внимание», «Тревога», «Нет данных», сохраняя числовое значение.

### Актуальное рабочее описание

Система должна непрерывно получать давление трёх газовых линий, преобразовывать сигналы 4–20 мА в bar, показывать текущее состояние на настенном экране, сохранять историю и в будущем уведомлять ответственных через MAX. Текущий объект следует считать лабораторным/демонстрационным стендом. Целевая система должна дополнительно получить утверждённые пороги, безопасный монтаж, резервирование, управление доступом, эксплуатационную документацию и приёмочные испытания.

### Что не подтверждено

- применение стенда в реальной реанимации;
- соответствие медицинским, метрологическим, электрическим и информационным требованиям;
- состав и серийные номера реально установленного оборудования;
- фактическая готовность каждого программного контура.

- Отключить heartbeat и registration packet на канале Modbus.

- `ping` и TCP connect на `502` успешны.

- Нет timeout/CRC/exception при серии запросов.

## 7. Настройка WB-MAI6

### Почему настройки по умолчанию не подходят

Официальная документация указывает, что каналы надо программно перевести в нужный режим. Для стандартного сигнала 4–20 мА используется код `0x1302`, decimal `4866`. Для датчика 0–16 bar проект предлагает шкалу `0…160`, чтобы получать значение в десятых долях bar и делить его на 10 в Node-RED.

### Подтверждённая карта адресов

| Газ | Канал | Тип, holding | Нижняя граница, holding i32 | Верхняя граница, holding i32 | Значение, input i16 |
|---|---|---:|---:|---:|---:|
| O₂ | IN1P | 5120 (`0x1400`) | 5128 (`0x1408`) | 5130 (`0x140A`) | 5380 (`0x1504`) |
| AIR | IN2P | 9216 (`0x2400`) | 9224 (`0x2408`) | 9226 (`0x240A`) | 9476 (`0x2504`) |
| N₂O | IN3P | 13312 (`0x3400`) | 13320 (`0x3408`) | 13322 (`0x340A`) | 13572 (`0x3504`) |

Формулы адресов официальной карты:

```text
type P     = 4096 × X + 1024
scale low = 4096 × X + 1032
scale high= 4096 × X + 1034
value P    = 4096 × X + 1284
```

### Команды настройки

Это безопасные по области действия шаблоны, но запись меняет конфигурацию устройства. Перед записью надо прочитать и сохранить старые значения. В `mbpoll` используется нулевая адресация `-0`; `-B` задаёт big-endian word order для 32-битных границ.

Чтение текущей конфигурации:

```bash
mbpoll -m tcp -a 65 -0 -r 5120  -c 1 -t 4     -o 3 -1 192.168.50.10
mbpoll -m tcp -a 65 -0 -r 5128  -c 1 -t 4:int -B -o 3 -1 192.168.50.10
mbpoll -m tcp -a 65 -0 -r 5130  -c 1 -t 4:int -B -o 3 -1 192.168.50.10
mbpoll -m tcp -a 65 -0 -r 9216  -c 1 -t 4     -o 3 -1 192.168.50.10
mbpoll -m tcp -a 65 -0 -r 9224  -c 1 -t 4:int -B -o 3 -1 192.168.50.10
mbpoll -m tcp -a 65 -0 -r 9226  -c 1 -t 4:int -B -o 3 -1 192.168.50.10
mbpoll -m tcp -a 65 -0 -r 13312 -c 1 -t 4     -o 3 -1 192.168.50.10
mbpoll -m tcp -a 65 -0 -r 13320 -c 1 -t 4:int -B -o 3 -1 192.168.50.10
mbpoll -m tcp -a 65 -0 -r 13322 -c 1 -t 4:int -B -o 3 -1 192.168.50.10
```

Запись IN1P / O₂:

```bash
mbpoll -m tcp -a 65 -0 -r 5120 -t 4     -o 3 -1 192.168.50.10 4866
mbpoll -m tcp -a 65 -0 -r 5128 -t 4:int -B -o 3 -1 192.168.50.10 0
mbpoll -m tcp -a 65 -0 -r 5130 -t 4:int -B -o 3 -1 192.168.50.10 160
```

Запись IN2P / AIR:

```bash

mbpoll -m tcp -a 65 -0 -r 9224 -t 4:int -B -o 3 -1 192.168.50.10 0

```

Запись IN3P / N₂O:

Проверка значений:

```bash
mbpoll -m tcp -a 65 -0 -r 5380  -c 1 -t 3:int16 -o 3 -1 192.168.50.10
mbpoll -m tcp -a 65 -0 -r 9476  -c 1 -t 3:int16 -o 3 -1 192.168.50.10
mbpoll -m tcp -a 65 -0 -r 13572 -c 1 -t 3:int16 -o 3 -1 192.168.50.10
```

### Интерпретация ошибки

- Для пересчитанного 16-битного регистра официальная карта указывает `0x7FFF`, то есть `32767`, как ошибку.
- В обсуждениях Wiren Board также встречается `0xFFFF` для иных/обычных регистров. Тип регистра и знаковость должны учитываться.
- `-32768` как специальный код ошибки в доступной официальной строке карты не подтверждён. Оставить его в Node-RED как защитный фильтр можно, но документировать как проектную защиту, а не как подтверждённый код WB-MAI6.

### Критерий успешной настройки

1. Тип каждого P-входа читается как `4866`.
2. Границы читаются как `0` и `160`.
3. Регистр значения не равен коду ошибки.
4. Изменение тестового давления/тока приводит к монотонному изменению значения.
5. При 4 мА ожидается около `0`, при 20 мА — около `160`; промежуточные точки проверены калибратором.
6. Настройка сохраняется после перезапуска питания.

## 8. Подключение датчиков

### Заявленная двухпроводная схема 4–20 мА

```text
+24 VDC ──> красный провод PT-506
чёрный провод PT-506 ──> INxP
iGND канала ──> 0 VDC блока питания
INxN ──> не используется для одного датчика на P
```

Официальная документация подтверждает, что вход WB-MAI6 пассивный, для пассивного датчика нужен внешний источник, а земля источника должна быть объединена с сигнальной землёй измерительного канала. В модуле есть внутренний шунт для измерения тока; внешний измерительный резистор обычно не требуется.

### Роль клемм

- `P` — положительный однополярный измерительный вход выбранного канала.
- `N` — второй однополярный вход или часть дифференциального подключения; в заявленной схеме одного датчика на P не используется.
- `iGND` — сигнальная земля аналоговых каналов. Это не защитный проводник PE.
- `GND` интерфейса/питания и `iGND` нельзя произвольно считать раздельными или взаимозаменяемыми: соединение выполняется по схеме производителя.

### Проверка мультиметром

1. При отключённом питании проверить полярность, целостность и отсутствие короткого замыкания.
2. В режиме DC voltage параллельно проверить примерно 24 V на питании датчика.
3. Для тока разорвать петлю и включить мультиметр последовательно; ожидать 4–20 мА.
4. После измерения тока вернуть щуп в гнездо напряжения: это снижает риск короткого замыкания при следующей проверке.
5. Для приёмки лучше использовать калибратор токовой петли на 4, 12 и 20 мА.

### Типовые ошибки

- перепутаны A/B RS-485;
- перепутана полярность токовой петли;
- `iGND` не соединён с 0 V источника;
- мультиметр в режиме тока подключён параллельно питанию;
- датчик заведён на N, а настроен P, или наоборот;
- канал оставлен выключенным либо выбран неверный тип;
- внешняя шкала задана в bar, а flow дополнительно делит на 10;
- один газ физически подключён к каналу другого газа;
- нет маркировки проводов и каналов.

## 9. Node-RED flow

### Заявленные модули

- Node-RED;
- `node-red-contrib-modbus`;
- `@flowfuse/node-red-dashboard`;
- `node-red-contrib-influxdb`.

Версии пакетов и совместимость не подтверждены: отсутствуют `package.json`, palette export и startup log.

### Заявленная структура

| Контур | Узлы/функции |
|---|---|
| Сбор | 3 × `modbus-read`: 5380/O₂, 9476/AIR, 13572/N₂O |
| Нормализация | `Normalize gas value` |
| Состояние | `Build dashboard state + clock`, `flow.gasState` |
| Время | `Clock tick` каждые 1 s |
| UI | `ui-template` для monitoring и history |
| История | фильтрация валидных значений → InfluxDB |
| Будущие оповещения | state builder → detector → message → HTTP request |

### Заявленная нормализация

```text
payload[0] → raw
raw ∈ {32767, -32768} или NaN → nodata
иначе pressure_bar = raw / 10

4.0 ≤ bar ≤ 6.0       → ok / НОРМА
3.5 ≤ bar < 4.0       → warn / ВНИМАНИЕ
6.0 < bar ≤ 6.5       → warn / ВНИМАНИЕ
bar < 3.5 или > 6.5   → alarm / ТРЕВОГА
```

### Что требуется уточнить

- Ветка ровно `6.0`: по указанным правилам это `ok`; ровно `6.5` — `warn`.
- Таймаут устаревания отсутствует в описании. Если Modbus замолчал после последнего корректного значения, UI не должен бесконечно показывать старую «Норму».
- Приоритет общего статуса не зафиксирован. Рекомендуемый безопасный вариант: `alarm` → `nodata` → `warn` → `ok`, при этом на карточках сохраняются индивидуальные состояния.
- Нужна защита от дребезга около порогов: гистерезис и/или выдержка времени.
- Медицинские пороги должен утвердить ответственный специалист; текущие значения — только тестовые.

### Clock tick и timezone

Clock tick должен обновлять время независимо от Modbus. Если Node-RED работает в Docker, проверить:

```bash
date
timedatectl status
docker exec <node-red-container> date
docker inspect <node-red-container> --format '{{json .Config.Env}}'
```

Рекомендуется явно задать `TZ=Europe/Moscow` и проверить синхронизацию NTP на хосте. Факт использования Docker не подтверждён.

### Что нужно получить для фиксации flow

- полный экспорт flow;
- список config nodes без секретов;
- версии Node-RED и npm-модулей;
- startup log;
- снимок успешного чтения всех трёх регистров;
- тест reconnect после отключения Ethernet/RS-485;
- таймаут `nodata`;
- тест граничных значений.

## 10. Dashboard

### Назначение

Главная страница `/dashboard/monitoring` — постоянный HMI-экран для врача. Она должна отвечать на два вопроса: «всё ли безопасно?» и «какое давление на каждой линии?».

### Согласованный по заданию макет

- сверху слева: дата/время и таблица O₂/N₂O/AIR;
- сверху справа: одна крупная цветная ячейка общего статуса;
- ниже: три строки или карточки газов;
- в карточке: название, крупное давление, статус, шкала зон, маркер;
- единица — `bar`, обозначение — `P`;
- расход `Q`, `м³/ч` не показывать без отдельного средства измерения;
- круговые gauge не использовать как основной элемент.

### Цвета и доступность

| Статус | Базовый цвет | Обязательное текстовое обозначение |
|---|---|---|
| Норма | зелёный | `НОРМА` |
| Внимание | жёлтый | `ВНИМАНИЕ` |
| Тревога | красный | `ТРЕВОГА` |
| Нет данных | серый | `НЕТ ДАННЫХ` |

Цвет не должен быть единственным носителем смысла. Нужны текст, контраст, крупный шрифт и устойчивость к дальнему просмотру.

### Требования 1366×768

- нулевой вертикальный и горизонтальный scroll;
- учёт реальной высоты браузера и панели kiosk;
- адаптация минимум к 1280×720, 1366×768 и Full HD;
- отсутствие hover-only функций;
- главный экран не зависит от мыши;
- значение `nodata` визуально не похоже на нормальное `0.0 bar`;
- потеря связи отображается за согласованный срок.

### Статус

Создание страниц и `ui-template` заявлено, но ни визуальный результат, ни CSS, ни маршруты не подтверждены. Поэтому dashboard нельзя считать прошедшим аудит.

## 11. История данных

### Заявленная модель

- measurement: `gas_pressure`;
- fields: `pressure_bar`, `raw`, `status_code`;
- tags: `gas`, `gas_name`, `status`;
- запись только корректных значений;
- отдельная страница `/dashboard/history`;
- периоды: 1 h, 24 h, 7 d, 30 d, произвольные `start/end`;
- фильтр газа.

### Противоречие bucket

В задании указано, что запись шла в `wb`, а чтение — из `rinir`. Актуальная версия не доказана. До получения flow и Influx-конфигурации нельзя утверждать, что `wb` является текущим bucket.

### Рекомендованное решение

Зафиксировать один bucket в environment/config node и использовать его и для записи, и для чтения. Если уже есть данные, сначала инвентаризировать оба bucket, затем выбрать:

- `wb` — если там находится актуальная серия и это имя принято владельцем;
- новое однозначное имя, например `gas-monitoring` — только при согласованной миграции.

### Что проверить

- версия InfluxDB и Flux/InfluxQL;
- organization, bucket, retention;
- типы fields не меняются между точками;
- tags не имеют неконтролируемой кардинальности;
- `nodata` не записывается как давление;
- временные метки соответствуют UTC/локальному отображению;
- данные переживают перезапуск;
- 30-дневный запрос не перегружает UI;
- CSS history-страницы помещается на целевом экране;
- пустая выборка и ошибка запроса отображаются отдельно.

## 12. Уведомления MAX

### Требуемая логика

- уведомлять о переходах состояний, а не о каждом Modbus-чтении;
- отдельно уведомлять об ухудшении и восстановлении;
- повторять активную тревогу через согласованный интервал;
- хранить токен в environment/secret storage;
- логировать результат доставки без токена.

Минимальная машина состояний на каждый газ:

```text
ok → warn       уведомление
ok → alarm      уведомление
warn → alarm    уведомление
alarm → ok      восстановление
nodata → ok     восстановление
любой → nodata  уведомление после выдержки
alarm → alarm   повтор через N минут
```

### Чего не хватает

- подтверждённого MAX API endpoint и формата;
- `MAX_BOT_TOKEN`;
- `MAX_CHAT_ID` или списка получателей;
- правил для `warn`, `alarm`, `nodata`;
- интервала повтора;
- рабочих часов/эскалации;
- шаблона сообщения;
- тестового чата;
- политики хранения секрета;
- подтверждения доставки и retry/backoff.

Реализация MAX в доступных материалах отсутствует. Финальный flow не формировался.

## 13. Открытые вопросы и противоречия

| Вопрос | Почему открыт | Что считать временной версией |
|---|---|---|
| Клинические пороги по O₂/AIR/N₂O | Нет утверждённого документа | Текущие пороги использовать только для стендовой демонстрации |
| Одинаковы ли пороги трёх газов | Не доказано | Не переносить в эксплуатацию без владельца требований |
| Общий статус при `alarm` одного газа и `nodata` другого | Приоритет не задан | Предложение: `alarm` выше `nodata`, но оба явно показать |
| Таймаут `nodata` | Не указан | Выбрать после измерения polling interval, например несколько пропущенных циклов |
| `32767`, `0xFFFF`, `-32768` | Разные форматы/источники | `32767` подтверждён для пересчитанного i16; остальные фильтры считать защитными |
| Bucket `wb` или `rinir` | Есть прямое противоречие | Ничего не переименовывать до инвентаризации |
| Реальное давление или расход | Есть только датчики давления | Показывать `P`, bar; `Q` убрать |
| Нужны ли расходомеры | Требование не определено | Не вычислять расход из одного давления |
| MAX | Нет API/получателей/правил | Оставить отдельным будущим контуром |
| Kiosk | Нет выбранного браузера и автозапуска | Сначала определить ОС-сессию и способ обслуживания |
| Резервирование | Нет требований | Для MVP не блокирует, для эксплуатации обязательно |
| Место установки | Не указано | Требуется обследование |
| Паспорт PT-506 | Отсутствует | Не считать диапазон/распиновку окончательно подтверждёнными |
| Версия WB-MAI6/firmware | Отсутствует | Считать карту адресов применимой только после сверки устройства |
| Актуальный flow | Отсутствует | Заявленную логику считать спецификацией, не deployed state |
